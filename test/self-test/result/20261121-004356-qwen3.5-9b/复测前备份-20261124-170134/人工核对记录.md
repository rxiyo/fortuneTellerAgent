# 人工核对记录

本记录只列已核对到的具体现象；“运行完成”不等于结果正确。其余案例请结合每个 JSON 的 `expected_checks` 和对应执行日志继续核对。

## chart_001 真太阳时修正量单位不一致

- 工具回执中的 `solar_correction` 为约 `-39.013`，单位为分钟。
- 模型最终回答将其写成了“约 -39.01 秒”，与工具数值的单位不一致；同一回答给出的钟表时间与真太阳时相差约 39 分钟。
- 这是本次实际运行中发现的结果表述错误，不能因为调用工具成功就认定该回答通过。完整输入、输出和日志见 [chart_001.json](chart_001.json)。

## chart_004 出生时辰未知时使用了假定时间

- 输入明确表示不知道具体出生时间；日志显示模型仍请求使用 `2000-08-12T00:00:00+08:00` 排盘。
- 该轮达到 360 秒时限后中断，没有产生完整最终回答。不能据此判断模型最终会不会解释这是临时假设；需要关注工具调用阶段不应将未知时间当作已知信息。
- 详细过程见 [chart_004.json](chart_004.json) 中的原始执行日志链接。

## context_001 旺衰查询先尝试了不存在的方法

- 第 3 轮模型先请求目录方法 `bazi.strength.build_strength`，工具返回目录中没有该方法。
- 该轮随后改为调用现有的 `bazi.strength.day_master_strength`，并获得结果。需把前一次错误与之后的自我纠正一起看，不能直接将整个案例判为失败。
- 见 [context_001.json](context_001.json) 和 [原始执行日志](执行日志/context_001.md)。

## location_002 未经确认推断出生省份

- 用户只说“出生城市是佛山”，没有提供省份；模型直接以 `name=佛山市`、`province=广东` 调用了地点工具。
- 该案例的预期是省份不明确时追问，因此工具虽返回广东佛山，不能视为通过了资料收集检查。
- 见 [location_002.md](location_002.md) 和 [原始执行日志](执行日志/location_002.md)。

## 古籍引用格式与证据链解析不一致

- `rag_001` 的回答使用 `【passage_id: 片段ID】`，当前证据节点会把整个括号内容当作 ID，导致 5 项被列为未解析；去掉 `passage_id:` 前缀后，这 5 个 ID 均能在该案例返回的古籍片段中找到。
- 同样地，`evidence_001` 的 6 项、`theme_003` 的 4 项，以及 `luck_004` 的 3 项带前缀 ID，去掉前缀后能在对应案例的 RAG 返回中找到。`luck_004` 中的 `【工具计算】` 和 `【我的解释】` 则被解析器误当作引用 ID。
- 这些结果表明回答格式与当前程序解析方式不一致；ID 能对应片段也不代表引用内容准确或适用于命盘。
- 见 [rag_001.md](rag_001.md)、[evidence_001.md](evidence_001.md) 及其同名原始日志。
